# План: заказы продукции

**Статус: запропоновано (ждёт согласования). Кода нет.**
Дата: 2026-11-07. Автор плана: Claude, по запросу владельца.

## 0. Что нужно (со слов владельца)

- Заказывать торгуемую продукцию (труна, вінок и т. п.) **отдельно** и **вместе с транспортом для покойного**.
- На каждом столе заказов ассортимент может отличаться.
- Номенклатуру брать из той же базы, что и для отчёта.
- Выбор товара: поле с поиском и подсказками, которое находит товар **по любому слову**, а не только с начала: «Труна Бейка спец 3 метра» должна находиться и по «бейка», и по «3 метра».
- Не нагружать базу запросами: номенклатуру кэшировать локально.

## 1. Что есть сегодня

- Каталог (`products`, `product_prices`) принадлежит модулю `reports`.
- Все подразделения видят **один и тот же** набор: товары `active && !archived`. Отдельного ассортимента по подразделениям **нет**.
- Цены хранятся по периодам; в одном месяце бывает две цены (старая и новая).
- В демо-каталоге 3 товара. **Реальный размер каталога мне неизвестен**: от него зависит порог решений в §6.
- Модули общаются только через `core`; один модуль не импортирует другой, поэтому «тянуть из базы отчётов» нужно через интерфейс, а не прямым запросом к таблицам `reports`.

## 2. Главное решение: где живут заказы

### Вариант A. Третья часть существующей заявки на транспорт

Рядом с «Доставка» и «Винос» появляется часть «Продукция». «Вместе с покойным» получается сам собой: одна заявка, один покойный, одна карточка. «Отдельно» — заявка только с частью «Продукция» (так же, как сегодня бывают заявки только с доставкой).

- Плюсы: одна форма и одна карточка, все даты/статусы/индикаторы («Терміново», «Військове», полоса дней, «Попереду в роботі») работают сразу.
- Минусы: если продукцию выполняет **другой человек**, нужен статус по части, а не по заявке; раздел начинает быть «Замовлення», а не «Транспорт».

### Вариант B. Отдельный модуль (`supply`)

Свои права, статусы, исполнитель и страница. Связь с транспортом необязательная: числовой `transport_order_id` без внешнего ключа между слайсами.

- Плюсы: чистое разделение; исполнитель и права отдельные.
- Минусы: «вместе с транспортом» требует инфраструктуры: через `core` отдавать список заявок стола, а если карточка транспорта должна показывать связанную продукцию — ещё и точка расширения в оболочке.

### Что решает выбор

1. **Кто выполняет заказы продукции?** Тот же диспетчер → вариант A. Другой человек/отдел → вариант B.
2. **Нужно ли видеть продукцию внутри карточки транспорта?**

**Рекомендация:** A, если исполнитель тот же; иначе B. Пока ответа нет, стартуем с фаз 1–2 (§9), которые одинаковы для обоих вариантов.

## 3. Доступ к каталогу

- `reports` отдаёт каталог через интерфейс в `core` (как `Notifier` и `SeedTools`): без импорта `reports` и без SQL по его таблицам.
- Элемент: `id`, `name`, `active`, текущая цена.
- **Цена фиксируется в строке заказа в момент заказа** (снимок имени и цены). «Цена периода» при переоценке посреди месяца неоднозначна; в `reports` уже есть функция «последняя цена».

## 4. Ассортимент по подразделениям

- Новое понятие, принадлежит модулю заказов (ключ — id товара).
- Пустой список у подразделения = «все активные товары».
- Явно: это **не меняет**, какие товары видны в форме месячного отчёта.
- Кто ведёт ассортимент — вопрос к владельцу (§10).

## 5. Поиск (спецификация)

Нормализация делается **один раз при загрузке каталога** и только для сопоставления; показывается имя как записано.

- нижний регистр;
- буквы, которые путают между украинской и русской раскладкой, сводятся к одной (і/и/ї, є/е, ґ/г), апострофы приводятся к одному виду;
- цифры отделяются от букв: «3м» → «3 м»;
- синонимы единиц: метр/метра/метрів → м; сантиметр → см.

Сопоставление:

- каждое слово запроса должно быть **началом какого-то слова** в названии, где угодно в нём;
- числа совпадают точно;
- если ничего не найдено: поиск по подстроке, затем замена раскладки EN→UK.

Порядок выдачи: совпадение с начала названия → с начала слова → как часто этот стол заказывает товар → по алфавиту. Совпавшие части подсвечиваются.

Компонент: универсальный примитив `ui/` по схеме ARIA combobox: ↑↓, Enter, Esc, строки по 44 px, подпись и подсказки для экранного диктора. Нативный `datalist` не используем (он рендерится на языке браузера и не умеет такой поиск).

Контрольные случаи (станут тестами):

| Запрос | Результат |
| --- | --- |
| «бейка» | «Труна Бейка спец 3 метра» |
| «3 метра», «3м», «3 м» | «Труна Бейка спец 3 метра» |
| «бей 3» | «Труна Бейка спец 3 метра» |
| «труна» | не находит «Вінок» |
| «ьуйка» (набрано в английской раскладке) | «Труна Бейка спец 3 метра» через замену раскладки |

## 6. Как не нагружать базу (ответ на прямой вопрос)

Честно: SQLite работает **внутри программы**, прочитать несколько тысяч строк стоит миллисекунды. Настоящая цена «поиска при вводе» — **сетевой запрос на каждое нажатие клавиши** через туннель, особенно с телефона.

Поэтому:

- **Один GET** отдаёт весь ассортимент подразделения целиком; **весь поиск идёт в памяти браузера**, запросов на каждое нажатие нет.
- **ETag** считается как хеш тела ответа; если не менялось — ответ 304. Счётчик ревизий между слайсами не нужен, работает и после перезапуска.
- TanStack Query: длинный `staleTime` и обновление при возврате на вкладку.
- По желанию копия в IndexedDB для мгновенного старта и работы без сети (в `platform/offline` уже есть заготовки).
- Нужен реальный размер каталога: если он порядка тысяч позиций, всё сказанное остаётся верным; если десятки тысяч, добавим индекс по префиксам.

## 7. Модель данных (эскиз)

Новые таблицы относятся к «Go-owned»: добавляются в `goOwned`, в `GoOwnedTables` и в фильтр `structure()` теста, **не** в `fresh.sql`. Деньги — целые копейки, количество — целое. Существующие таблицы не меняются.

- `product_orders`: подразделение, покойный (необязательно), нужен к дате, статус, кто создал, времена. При варианте A — это часть `transport_orders` (новые поля/таблица строк).
- `product_order_items`: товар, **снимок имени**, количество, **снимок цены**.
- `organisation_products`: подразделение, товар (ассортимент; пусто = все).

## 8. Статусы, уведомления, показатели

- Статусы: по потоку транспорта (вариант A) или собственные (вариант B). Индикаторы дат и срочности те же, что у транспорта.
- Показатели добавляются в «Показники» через уже готовый хук `Dashboard` (выручка по заказам, число заказов, срочные).
- Напоминания: по решению владельца (§10).

## 9. Этапы

1. Интерфейс каталога в `core`, ассортимент подразделений, компонент поиска (с тестами по §5).
2. Заказы продукции отдельно.
3. Связь с транспортом (по выбранному варианту).
4. Блоки для «Показники» и напоминания.

После каждого этапа: полный прогон (Go, vitest, сборка, e2e) и снимки экрана.

## 10. Вопросы для согласования

1. **Вариант A или B**: кто выполняет заказы продукции (тот же диспетчер или другой человек)? Нужно ли видеть продукцию внутри карточки транспорта?
2. **Кто ведёт ассортимент** каждого подразделения (администратор, руководитель, сам стол)?
3. **Нужны ли цены и оплата** в заказе? Это связано с нерешённым вопросом про статус «оформлено/оплачено».
4. **Попадает ли заказанная продукция в месячный отчёт** автоматически? Осторожно: риск двойного учёта (продали по заказу и снова вписали в отчёт).
5. **Действует ли отсечка 15:00** (заказ на завтра до 15:00) и для продукции? Едет ли продукция с машиной транспорта?
6. **Реальный размер каталога** (сколько активных товаров) и сколько примерно позиций бывает у одного стола.
