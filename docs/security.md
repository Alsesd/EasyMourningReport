# Security notes

Last reviewed: 2026-11-06 (govulncheck: nothing the code calls; `npm audit`: 0; manual review of sessions, passkeys, transport isolation, the administrators' session list, the update path and the new first-run/password rules; no `dangerouslySetInnerHTML`/`innerHTML` anywhere in the frontend; the CSP is unchanged and covers the print page, which uses no inline script).

## Dependencies

- Go: built with the patched toolchain pinned in `go.mod` (`toolchain go1.26.10`); `govulncheck` on the source finds nothing the code calls. Re-run `govulncheck ./cmd/... ./internal/...` and `govulncheck -mode binary dist/legkyi.exe` before each release.
- Known false positive: binary mode lists GO-2026-5932 (`x/crypto/openpgp`). The program links only `x/crypto/md4` and `ripemd160` (through the Excel library) and no `openpgp` package, so it is not affected. No tagged fix exists yet.
- Frontend: `npm audit` reports 0 vulnerabilities (react-router 7.18+, vitest 5, a `minimatch` override in `package.json` for the linter chain). Do not run `npm audit fix --force`.

## What is in place

- **Sessions (server-side):** the cookie carries a random 32-byte token signed with HMAC-SHA256; the server keeps only the SHA-256 of the token in `user_sessions` (so a database copy or backup holds no usable credential). Logging out, changing your own password, an administrator resetting a password, and disabling or deleting an account end the sessions immediately; sessions survive an app restart and expire after 7 days. Cookie flags: `HttpOnly`, `SameSite=Lax`, and `Secure` when `COOKIE_SECURE=1` or when the request reached the local cloudflared over https.
- **Device-bound sessions (rolling device token):** every session is tied to the browser it was issued to by a second cookie (`device`, `HttpOnly`, signed) whose token is stored only as a SHA-256 in `session_devices`. The token is replaced every 10 minutes of use (the previous one stays valid for 30 minutes so parallel requests and a lost response do not sign anyone out). A request whose session cookie is not signed by this server, or whose device token does not match, gets **no answer at all** (the connection is closed without a byte) and a mismatched session is revoked on the spot, so a copied cookie is useless and a probe learns nothing. (Behind the Cloudflare tunnel the visitor will usually see Cloudflare's 502 page instead of silence.) Page loads (not `/api/v1`) with a cookie this server never signed are served signed out and the stale cookies are expired, so a changed `SECRET_KEY` or another app's cookie of the same name cannot lock anyone out of the login page. Sessions created before this existed are invalid after the upgrade (users sign in once).
- **Session list for administrators:** «Адміністрування → Сеанси» (permission `platform.users.manage`, held by the platform administrator role) lists every signed-in device of every employee with the browser and system (from the User-Agent), the address the session started from, when it started and its last activity, and can end one session or all sessions of a user (audited). The list keeps each session's address and a User-Agent (shown only as "browser · system") for as long as the session exists, and only administrators can read it; tell staff that signing in records these two details. Use it for a lost phone or a departed employee; changing or resetting the password also ends all of a user's sessions.
- **Passkeys (biometric sign-in, WebAuthn):** users register the fingerprint, face or screen lock of a device in the account menu and sign in with one tap. After a password sign-in on a device without a key, the app offers once to turn biometric sign-in on; the answer (`legkyi.biometric`: agreed/declined) is kept in that browser only and holds nothing secret. A device that agreed opens the device prompt by itself on the login page (not right after an explicit sign-out; the password form is always there). Only discoverable credentials with user verification are accepted (ES256 or RS256, no attestation); the server stores the public key and a signature counter and rejects a counter that does not advance (cloned authenticator). Challenges are single-use and expire in 5 minutes; failures are rate limited per IP and audited. Passkeys need https (the tunnel provides it) and are bound to the host name: with a quick tunnel (`trycloudflare.com`, new name on each start) they stop working when the name changes, so use a named tunnel (`TUNNEL_TOKEN`) or pin `PASSKEY_RP_ID`.
- **Automatic updates:** release builds (stamped with their tag, commit and build time by `scripts/build_go.sh`) check GitHub's "latest release" about 10 minutes after start and then every `AUTO_UPDATE_CHECK_HOURS` (6) hours, over https only (redirects included), with a fixed generic User-Agent. A release counts as newer when its tag differs from the running one, it was published after this build was made, and its file for this platform is not byte-for-byte the running program (a release that was only re-tagged or renamed is not an update) (tags are free text and are never compared with each other). The asset for the platform is downloaded to a temporary file in the program's folder, size-capped, and its SHA-256 must match the release's `SHA256SUMS.txt`; then a `before-update` backup is taken, the file is replaced (Linux: atomic rename; Windows: the running exe is renamed to `legkyi.exe.old` and kept for a manual rollback), and the program restarts after a normal graceful shutdown. Development builds (no stamp), Docker and `go run` never update; `AUTO_UPDATE=0` turns it off and then the admin page only offers a manual button. **Trust model:** the checksum comes from the same release as the file, so it detects a damaged download but not a compromised repository or release: whoever can publish a release on GitHub can run code on every installation. Protect the repository accordingly (2FA, restricted write access) or set `AUTO_UPDATE=0`.
- **Cloudflare Access (optional, off by default):** with `CF_ACCESS_TEAM_DOMAIN` (e.g. `myteam.cloudflareaccess.com`) and `CF_ACCESS_AUD` (the application's AUD tag) set, every request that came through the tunnel (from the local cloudflared: loopback peer plus the `Cf-Connecting-IP` header the edge sets itself) must carry a valid `Cf-Access-Jwt-Assertion`, otherwise it gets a 403 with a log line saying why. The token is verified as RS256 only against Cloudflare's published keys (looked up by `kid`, refetched when a key id is unknown at most once a minute, last good keys kept if Cloudflare is unreachable, refused while no keys are known), with `iss`, `aud`, `exp` and `nbf` checked (60 s clock leeway). The check sits outside the session layer, so refused traffic never reaches sessions. Local access (no `Cf-Connecting-IP`) is never touched, so a wrong setting can be fixed on the machine itself. Access needs a **named tunnel on your own domain** (`TUNNEL_TOKEN`): a quick tunnel (`trycloudflare.com`) cannot be put behind Access, and with Access on its traffic is refused (the app warns at start). Setup, in the Cloudflare Zero Trust dashboard (labels change, see Cloudflare's "Self-hosted applications" and "One-time PIN" pages): add a self-hosted application for the tunnel's hostname, add a policy allowing the staff e-mail addresses (login method *One-time PIN*), copy the application's *AUD tag* into `CF_ACCESS_AUD` and your team domain into `CF_ACCESS_TEAM_DOMAIN`, restart. Access guards the door; the app's own password or passkey sign-in still follows.
- **First start:** a new database holds only the administrator (no divisions, no other roles, no data). New and changed passwords need 8+ characters with a lowercase letter, an uppercase letter and a digit; the generated first-start password and `ADMIN_PASSWORD` must comply, a weaker `ADMIN_PASSWORD` stops the start. Existing passwords still sign in and are checked only when changed.
- **Transport isolation:** a division's employees see and change only their own division's orders. Holding `transport.orders.manage` or `view_all` widens reading (and, for `manage`, replying with a status and naming bearers) to every division, but editing and cancelling an order is always limited to the caller's own division, so a person who holds both `create` and `manage` cannot rewrite another division's order.
- **CSRF:** every non-GET request must carry a same-origin `Origin` or `Referer`.
- **Sign-in:** per login+IP (5 failures), per IP (20) and per login (30) limits within 15 minutes, answered with `429` and `Retry-After` (in memory); the password is checked before account state is revealed; an unknown login costs the same time as a wrong password (a short window remains for accounts whose password has not yet been upgraded, see below).
- **Session lifetime:** a session lasts 7 days (server-side row and cookie).
- **Error log:** `system.LogRing` keeps the program's warnings and errors for the health page and mirrors them to `<data>/logs/legkyi.log` (0600, about 1 MB, one rotation). URLs are reduced to their host and a 5xx is logged without its query string, so tokens and personal data in query strings do not reach the log. The log is visible only to `platform.system.manage`.
- **Management dashboard:** `management.dashboard.view` is read-only and the only gate of `GET /dashboard`; the figures are aggregated server-side from the other modules, and no write route belongs to it.
- **Client address:** the forwarded header is honoured only from the local cloudflared, and the right-most untrusted hop is used, so a client cannot spoof it behind Cloudflare.
- **Passwords:** PBKDF2-HMAC-SHA256, 600,000 iterations, random salt, self-describing format (`pbkdf2_sha256$600000$salt$hash`). Hashes from earlier releases (200,000 iterations) still verify and are rewritten when that user next signs in successfully. Every new or changed password needs 8+ characters with a lowercase letter, an uppercase letter and a digit (any alphabet, Cyrillic included; `platform.PasswordProblem`); existing passwords keep working until changed. Expect roughly a second per sign-in on a phone.
- **Headers:** Content-Security-Policy (scripts only from the app's own files, no framing), `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, and `Strict-Transport-Security` (180 days, no subdomains, no preload) on requests that arrived over https through the tunnel.
- **Limits:** JSON bodies 8 MB, Excel upload capped, read/idle/header limits on the server (no write timeout so backup downloads can stream).
- **Data access:** every API route goes through a permission check; organisation-scoped handlers resolve records through the caller's organisation (other organisations' records answer 404). SQL is parameterised; the only concatenated clauses are fixed strings.
- **Files:** on Linux/macOS/Android the program runs with umask 077 and tightens the database, WAL files, secret, backups and tunnel folder to owner-only at start. On Windows access is governed by NTFS permissions: keep the program's folder in a location only the service account and administrators can read (for example remove "Users" from its ACL).
- **Tunnel token:** passed to cloudflared through its environment (not the command line) and stored with mode 0600.
- **Release workflow:** the tag input goes through an environment variable and is validated; the exe can be signed when the repository has the secrets `WINDOWS_CERT_PFX` and `WINDOWS_CERT_PASSWORD` (this step has not been exercised yet).
- **Web Push:** the VAPID private key is `<data>/vapid.key` (0600, created once; or `VAPID_PRIVATE_KEY`). It is kept out of the database on purpose, so a backup never carries a key that can send as this server; losing it only means browsers must subscribe again. Subscriptions hold each browser's public key and auth secret (not credentials of this server), are owned by the user signed in on that browser, and are deleted at sign-out. The server only POSTs to https push-service hosts on an allowlist (no IP addresses, no other ports), so a registered endpoint cannot be used to reach internal addresses.

## Rolling back to the Python release

Accounts whose password hash was upgraded cannot sign in to the Python release (it only knows the old format), and the `user_sessions` table is ignored by it. A rollback therefore means restoring the backup taken before switching to Go.

## Known limitations

- The sign-in limiter is in memory and resets when the app restarts; only someone with host access can restart it, and they already hold the database.
- Until every account has signed in once after the upgrade, a sign-in for an account on an old hash takes less time than one on the new hash, and an unknown login takes the new-hash time.
- The exe is unsigned unless you add a certificate (SmartScreen warning). Anyone who can read the program's folder can read `reports.db`, `secret.key` and the saved tunnel token.
- `style-src` allows inline styles because the UI sets style attributes; scripts are strictly limited to the app's own files.
- A passkey is a second way in, not a second factor: an account with a password can still sign in with the password alone.
