Легкий, надійний та зручний веб-застосунок для збору та обробки щомісячних товарних звітів із кількох магазинів. Він допомагає автоматизувати рутинну роботу адміністратора, скорочує помилки при підрахунках і забезпечує прозорий контроль над звітами, цінами та історією змін.

## Про проект

`EasyMourningReport` призначений для компаній, де кілька торгових точок регулярно подають звіти про продажі. Замість ручного ведення Excel-таблиць або розкиданих форм, система централізує весь процес в одному веб-додатку.

Адміністратор:
- веде каталог товарів та цін;
- додає магазини та користувачів;
- контролює звіти по місяцях;
- переглядає журнал дій та історію змін.

Магазин:
- входить у систему;
- обирає місяць;
- вносить лише кількості товарів;
- зберігає чернетку або надсилає звіт;
- отримує автоматично підраховані суми.

## Чому це корисно

- зменшує ручний ввод даних;
- знижує ризик помилок у підрахунках;
- спрощує контроль за кількома магазинами;
- зберігає історію змін цін та звітів;
- дозволяє керувати процесом без окремого складного ERP-пакету.

## Основні можливості

- Управління товарами та їхніми цінами
- Масове створення товарів з Excel (.xlsx): колонка A — назва, колонка B — ціна
- Експорт зведеного звіту в Excel (.xlsx): назва, ціна, звітована кількість і сума
- Керування магазинами та обліковими записами
- Формування щомісячних звітів
- Автоматичний розрахунок сум
- Зведені звіти по місяцях
- Журнал дій та аудиту
- Історія змін цін з підтримкою місячної логіки
- Редактор ціни без варіантів: одне широке поле та розгортувана історія змін за місяць
- Необмежена кількість змін ціни одного товару протягом місяця зберігається в послідовності; у звіті пропонуються всі унікальні ціни, що діяли в цьому місяці
- Клієнтське відображення каталогу, звітів, зведення та журналу через Alpine.js і REST API v1 без перезавантаження сторінки
- Архівування товарів і магазинів замість безповоротного видалення
- Автоматичні резервні копії бази даних
- Безпечне зберігання паролів через PBKDF2-хешування
- Підтримка запуску як локального веб-додатку або Windows EXE

## Структура проекту

```text
EasyMourningReport/
├── app/
│   ├── core/             # Інфраструктура (paths, security, ratelimit, ui, dependencies)
│   ├── db/               # SQLModel-моделі, сесії, репозиторії, міграції та backup
│   ├── services/         # Чиста бізнес-логіка (pricing, excel)
│   ├── routes/           # HTML-маршрути та версійований REST API v1
│   ├── dto.py            # Типізовані запити й відповіді REST API
│   ├── static/           # CSS, JS-клієнти, PWA та статичні ресурси
│   ├── templates/        # Шаблони Jinja2
│   └── main.py           # Композиція FastAPI, життєвий цикл і middleware
├── tests/                # pytest, FastAPI TestClient та ізольовані тести БД
├── .github/workflows/    # Тести та збірка Windows EXE через PyInstaller
├── DOCS.md               # Архітектурна та технічна документація
├── README.md
├── pyproject.toml
├── poetry.lock
├── run.py                # Головна точка входу (uvicorn)
├── flake.nix             # Nix flake для автоматизації на Linux
├── start.bat             # Запуск Windows
├── tailscale-helper/     # Ізольований tsnet-вузол та reverse proxy для Funnel
└── setup-windows-uvicorn.ps1 # Одноразове налаштування команди uvicorn у PowerShell
```

Архітектура розділена за відповідальністю: `main.py` лише збирає FastAPI-застосунок, `routes/` відповідає за HTTP, `services/` — за бізнес-логіку, `db/models/` — за SQLModel-схему, а `db/repositories/` — за запити до даних. Внутрішні пакети не переекспортують функції через динамічні фасади: імпортуй символ безпосередньо з модуля, де його визначено.

## Вимоги

Перед запуском переконайтеся, що у вас встановлено:

- Python 3.10 або новіше
- Nix with flakes enabled
- Git

Для Windows також можна використовувати готовий `start.bat` або скомпільований `.exe` із релізу.

## Встановлення

### 1. Клонування репозиторію

```bash
git clone https://github.com/Alsesd/EasyMourningReport.git
cd EasyMourningReport
```

### 2. Встановлення залежностей

Poetry є єдиним джерелом залежностей проєкту; версії та транзитивні залежності фіксуються у `poetry.lock`.

```bash
poetry install
```

У Windows, якщо команда `poetry` не доступна в PATH, можна використовувати `python -m poetry install`. Для відтворюваного середовища не встановлюйте залежності застосунку окремо через `pip`.

## Запуск

### Варіант 1: запуск у Nix dev shell

```bash
nix develop
poetry install
serve
```

Nix надає Python і Poetry, а саме `poetry.lock` визначає Python-залежності. Команду `poetry install` потрібно виконати після першого клонування або після зміни залежностей. Для автоматичного перезавантаження під час розробки використовуйте `serve --reload`.

### Варіант 2: запуск через Python

```bash
python run.py
```

Після запуску відкрийте у браузері:

```text
http://localhost:8000
```

### Варіант 3: запуск на Windows через `start.bat`

```bat
start.bat
```

Цей сценарій запускає локальний сервер. Публічний доступ керується окремо в розділі **Налаштування → Tailscale Funnel**; системний Tailscale CLI та його daemon не потрібні для вбудованого helper.

#### Як запускати просто `uvicorn` у Windows

Один раз запустіть PowerShell у корені проєкту та виконайте:

```powershell
powershell -ExecutionPolicy Bypass -File .\setup-windows-uvicorn.ps1
```

Закрийте й відкрийте PowerShell. У корені проєкту команда працюватиме коротко:

```powershell
uvicorn --app-dir . app.main:app --reload
```

Скрипт додає функцію `uvicorn` до вашого PowerShell-профілю. У каталозі, де є `pyproject.toml`, вона автоматично запускає Uvicorn через Poetry; в інших каталогах передає виклик звичайному глобальному `uvicorn`, якщо він установлений. Це налаштування виконується один раз для вашого облікового запису Windows.


### Варіант 4: запуск готового EXE

Якщо ви завантажили реліз із GitHub:

1. Розпакуйте архів;
2. Запустіть `start.bat` або `LegkyiZvit.exe`;
3. Відкрийте адресу `http://localhost:8000`.

Під час першого запуску пароль адміністратора генерується автоматично і виводиться в консоль. Збережіть його у безпечному місці.

## Як користуватися застосунком

### Для адміністратора

1. Відкрийте панель налаштувань.
2. Додайте товари та встановіть актуальні ціни.
3. Створіть магазини та облікові записи працівників.
4. Переглядайте складені звіти за місяць.
5. Блокуйте або розблоковуйте окремі звіти.
6. Перевіряйте журнал активностей та історію змін.
7. Відновлюйте архівовані товари або магазини за потреби.

### Для магазину

1. Увійдіть до системи під логіном магазину.
2. Перейдіть у розділ "Звіт".
3. Виберіть потрібний місяць.
4. Введіть кількості товарів.
5. Збережіть чернетку або надішліть звіт.
6. Після відправлення звіт блокується до розблокування адміністратора.

## Як працює логіка системи

- Адміністратор визначає товарний каталог та ціни.
- Кожен магазин вводить кількості за обраний період.
- Сервер автоматично обчислює суми на основі актуальних цін.
- При зміні ціни система зберігає історію, щоб правильне підрахування працювало для різних місяців.
- Товари та магазини, які вже брали участь у звітах, не видаляються без попередження: вони архівуються.
- Усі дії учасників системи фіксуються в журналі аудиту.

## Безпека

- Паролі зберігаються у вигляді PBKDF2-хешів із випадковою сіллю.
- Адміністративний пароль генерується автоматично при першому запуску.
- Логіни магазинів унікальні та нечутливі до регістру.
- Дублікати назв та логінів відхиляються із поясненням.
- Система автоматично створює резервні копії даних перед важливими змінами.

## Резервні копії

Додаток автоматично зберігає резервні копії бази даних:

- під час запуску;
- під час зупинки;
- раз на годину при зміні даних;
- перед видаленням важливих елементів.

Резервні копії зберігаються в каталозі `backups/`.

## Тести

Запуск у Nix dev shell:

```bash
nix develop
test
```

Команда `test` запускає pytest і зупиняється з помилкою, якщо тести не пройшли або покриття застосунку нижче 95%. Для точкового запуску можна передати аргументи, наприклад `test tests/test_fastapi.py -q`.

Тести охоплюють бізнес-логіку, репозиторії, маршрути й HTTP-поведінку FastAPI через TestClient. Мінімальний поріг покриття коду застосунку — 95%; штучно зламаних тестів немає.

## Розробка та збірка standalone EXE (PyInstaller)

Windows-реліз збирається як один автономний файл за допомогою PyInstaller; CI спершу компілює окремий Tailscale helper на Go та вкладає його в EXE.

Для локальної збірки на Windows із установленим Python і Poetry:

```powershell
python -m poetry install
python -m poetry run python -m pip install pyinstaller==6.16.0
Invoke-WebRequest -Uri "https://cdn.jsdelivr.net/npm/alpinejs@3.17.4/dist/cdn.min.js" -OutFile app/static/alpine.min.js
if ((Get-Item app/static/alpine.min.js).Length -lt 10000) { throw "Alpine runtime download was incomplete." }
# Build the isolated tsnet helper first
cd tailscale-helper
go mod download
go build -trimpath -ldflags "-s -w" -o tailscale-helper.exe .
cd ..
python -m poetry run pyinstaller --noconfirm --clean --onefile --console --name LegkyiZvit --add-data "app/templates;app/templates" --add-data "app/static;app/static" --add-binary "tailscale-helper/tailscale-helper.exe;." --collect-all fastapi --collect-all starlette --collect-all sqlmodel --collect-all sqlalchemy --collect-all jinja2 --collect-all openpyxl --collect-all uvicorn run.py
```

Готовий файл: `dist/LegkyiZvit.exe`. У ньому містяться Python runtime, залежності, HTML-шаблони та статичні ресурси. Для звичайного використання не потрібно окремо переносити каталоги `lib/` або `app/`.

Існуючий Windows workflow автоматично запускає тести, збирає EXE, запускає упакований застосунок для HTTP smoke-тесту та завантажує артефакт. Для тегів `v*` і `Soup.v*` той самий workflow прикріплює EXE до GitHub Release. Перевірки виконуються до публікації; невдалий тест або smoke-тест зупиняє процес.

Дані користувача не зберігаються у тимчасовій теці PyInstaller. `reports.db`, `secret.key` та резервні копії залишаються в каталозі даних поруч із EXE, якщо він доступний для запису; інакше застосунок використовує `%LOCALAPPDATA%\\LegkyiZvit`. Для явного вибору каталогу можна задати `LEGKYI_DATA_DIR`.

Докладніше про архітектуру, запуск, збереження даних і перевірки дивіться у [DOCS.md](DOCS.md).

## Розгортання через Tailscale Funnel

У розділі **Налаштування → Tailscale Funnel** працює вбудований app-specific helper на базі Tailscale `tsnet`. Він створює окремий вузол для застосунку, запускає HTTPS reverse proxy та зберігає стан пристрою у приватному каталозі даних. Не потрібно встановлювати системний Tailscale CLI або окремо запускати daemon.

1. Підтвердьте попередження про публічний доступ.
2. Залиште поле auth key порожнім, щоб пройти браузерну авторизацію, або введіть тимчасовий/reusable key, якщо це відповідає вашій політиці tailnet.
3. Якщо потрібна авторизація, відкрийте посилання, яке показує панель, і завершіть вхід.
4. Після успішного підключення панель показує публічний HTTPS URL.

Auth key передається дочірньому процесу через stdin, не аргументами командного рядка чи змінними середовища, і не зберігається на диску. Стан вузла та явне ввімкнення Funnel зберігаються для наступного запуску; вимкнення в панелі зупиняє helper і скасовує автозапуск. Funnel доступний лише якщо його дозволено політиками tailnet.

## Поради для використання

- Не видаляйте вручну каталог `backups/`.
- Зберігайте файл `secret.key` у безпеці.
- Під час перенесення середовища копіюйте `reports.db` та `secret.key` разом.
- Для продакшн-середовища краще використовувати стабільний запуск через `uvicorn` або інший серверний процес.
